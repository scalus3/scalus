# LLM Developer Experience for Scalus – Design

Date: 2026-08-02
Status: Approved

## Goal

Let developers who use LLM coding agents (Claude Code, Cursor, Codex, Copilot)
write correct Scalus code on the first try. Attack the main failure mode: LLMs
hallucinate Scalus APIs because they train on old versions or on Aiken/PlutusTx.

Target: all agentic coding tools. Claude Code is the reference implementation.

Build order: docs site layer → scaffold layer → smoke eval → plugin layer.

## Layer 1: Docs site (scalus.org)

Four fetchable plain-text artifacts. All are generated, never hand-maintained,
except the `llms.txt` index.

### `/llms.txt` (exists, extend)

Keep the current index in `scalus-site/public/llms.txt`. Add links to the three
new artifacts below, with one line each that tells an agent when to fetch which.

### `/llms-full.txt` (new)

All docs pages concatenated as one markdown file.

- A build script in `scalus-site/scripts/` reads `content/**/*.mdx`.
- It strips MDX constructs: `import`/`export` lines, JSX components,
  frontmatter. It keeps headings, prose, and code blocks.
- Pages appear in sidebar (`_meta.js`) order, each prefixed with its canonical
  URL so agents can cite sources.
- The site build fails if generation fails (no silent staleness).

### `/llms-api.txt` (new)

A condensed, version-pinned API cheatsheet generated from Scalus source at
release time. This is the primary anti-hallucination artifact.

- An sbt task (in the scalus build) extracts public signatures plus the first
  scaladoc sentence for these surfaces:
  - `scalus.prelude` (List, Option, AssocMap, functions)
  - `scalus.builtin` (Builtins, ByteString, Data)
  - Validator traits (`Validator`, `ParameterizedValidator`,
    `DataParameterizedValidator`) and `@Compile`/`PlutusV3.compile`
  - `scalus.cardano.txbuilder.TxBuilder` and ledger domain types
  - Testkit entry points (Emulator, EvalTestDsl, budget assertions)
- The header pins the version, e.g. `Scalus 1.0.0`.
- The release workflow regenerates it and fails if extraction breaks.

### `/llms-examples.txt` (new)

A curated corpus of working code. LLMs imitate working code better than they
follow prose.

- Built from `scalus-examples` sources: the 21 Cardano Blueprint example
  validators with their tests. HTLC (the gold standard) comes first.
- Each entry: one-line description, validator source, test source.
- Generated by a script at site build time from the checked-out repo.

### Per-page markdown

Serve every docs page as plain markdown at `<page-url>.md` via a build-time
copy of the stripped MDX into `out/`. Agents that follow `llms.txt` links get
markdown, not HTML.

## Layer 2: Scaffold (g8 templates)

`hello.g8` and `validator.g8` (in `scalus3/`) make every new project AI-ready.

### `AGENTS.md`

Templates ship an `AGENTS.md` at project root with:

- Build and test commands (sbt and scala-cli variants).
- On-chain subset rules: what `@Compile` code may use, no stdlib collections,
  compare via `a.toData == b.toData`, no fully qualified names, param encoding
  gotchas.
- Common pitfalls (from memory: validator tests need clean, dual ExUnits
  baselines, etc. – genericized to user-project relevance).
- URLs of the four scalus.org artifacts, with guidance on when to fetch which.

`CLAUDE.md` in the templates is a one-line pointer to `AGENTS.md`.

### Skills

Templates ship `.claude/skills/` with the five Scalus skills (see below).

## Skill consolidation

`scalus-skills/` in the scalus repo becomes the single source of truth for
five skills:

1. `contract` – write validators (move from `~/.claude/skills`, genericize)
2. `contract-test` – test validators (move from `~/.claude/skills`, genericize)
3. `local-development` – Emulator and TxBuilder (move from `.claude/skills/`)
4. `optimize-contract` – budget optimization (already there)
5. `smart-contract-security-review` – pre-deploy audit (already there)

Genericize means: remove paths and assumptions tied to the scalus repo itself;
skills must work in a user project that depends on the published Scalus
artifacts.

The scalus repo's own `.claude/skills/` entries become symlinks into
`scalus-skills/` so maintainers keep dogfooding the shipped skills.
Personal workflow skills (`precommit`, `changelog`) stay out.

## Layer 3: Smoke eval (release CI)

A scripted eval converts docs quality into a pass/fail signal:

1. Scaffold a fresh project from `validator.g8`.
2. Run `claude -p` with 3–5 canonical tasks, e.g. "write an HTLC validator
   and tests", "add a mint policy", "optimize this validator's budget".
   The agent has only the shipped context (AGENTS.md, skills, fetchable
   artifacts).
3. Pass = project compiles and tests are green.

Triggers: manual dispatch plus the release workflow. Not on every push.

## Layer 4: Plugin (later)

A thin Claude Code plugin that packages `scalus-skills/` for one-command
install (`/plugin install scalus`) into existing projects. No MCP server for
now. Built last; adds distribution, no new content.

## Versioning and sync

- Source of truth for skills: `scalus-skills/` in the scalus repo.
- g8 templates copy skills at template-release time.
- Generated artifacts (`llms-full.txt`, `llms-api.txt`, `llms-examples.txt`)
  regenerate in the release workflow and carry the release version.

## Error handling

- Site build fails when `llms-full.txt` or `llms-examples.txt` generation
  fails.
- Release workflow fails when the API cheatsheet extractor breaks.
- Smoke eval failure blocks the release checklist item, not the build.

## Out of scope

- MCP server for docs.
- Cursor/Copilot-specific rule files beyond `AGENTS.md`.
- Full eval matrix across models and tools.
