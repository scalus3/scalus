# SSZ arithmetic reference vectors

`ssz-v0.1.0.json` contains 86 positive arithmetic cases generated by running the executable Python code of **ethereum/ssz-specs v0.1.0**, pinned at **`7bce07ff7d51b1a3c66ff4e2bd3233ac248ede70`**. `ssz-v1.5.0.json` is retained only as a legacy arithmetic cross-check. All 42 legacy cases match the maintained implementation byte for byte.

The maintained sources actually executed are:

- [`src/ssz/trees.py`](https://github.com/ethereum/ssz-specs/blob/7bce07ff7d51b1a3c66ff4e2bd3233ac248ede70/src/ssz/trees.py): `merkleize(chunks, limit)`.
- [`src/ssz/chunks.py`](https://github.com/ethereum/ssz-specs/blob/7bce07ff7d51b1a3c66ff4e2bd3233ac248ede70/src/ssz/chunks.py): zero chunks, cached zero subtrees and `zero_tree_root`.
- [`src/ssz/gindex.py`](https://github.com/ethereum/ssz-specs/blob/7bce07ff7d51b1a3c66ff4e2bd3233ac248ede70/src/ssz/gindex.py): integer generalized-index depths, branch indices and descending `get_helper_indices`.
- [`src/ssz/verification.py`](https://github.com/ethereum/ssz-specs/blob/7bce07ff7d51b1a3c66ff4e2bd3233ac248ede70/src/ssz/verification.py): `calculate_merkle_root` and `calculate_multi_merkle_root`.

The harness imports the unmodified package source and runs each hash in a fresh Python process with `uv run --with <pinned-source-directory> generate_maintained_vectors.py --hash <sha256|blake2b256> --output <json>`. The SHA run uses the original hash. The BLAKE run binds `hashlib.sha256` to BLAKE2b-256 **before importing any SSZ module**, so both node hashing and the initialized zero cache use BLAKE2b. An independent fold checks zero subtrees at heights 1 through 15 in each process. No cached SSZ objects cross the hash boundary. The generator and downloaded sources are kept outside the repository.

Inputs are deterministic: element `i` is ASCII `element-{i % 7}`. Every occupied chunk is BLAKE2b-256 of that element in both runs. Changing the node hash leaves those chunks unchanged. Depths are 1, 2, 3, 4, 5, 6 and 15. Each depth covers counts 0, `max(1, capacity * 3 // 5)` and capacity, plus 1, 3, 5 and capacity-1 when in range and not already present. There is no length mixing. This gives 43 cases per hash, including empty, partial, full and duplicate-rich trees.

Single positions are the sorted distinct set `{0, capacity - 1, count // 2, max(0, count - 1)}`. `occupied` is determined solely by `position < count`, not by any reference verifier verdict. Nonempty inputs have multiproof queries for the first `min(4, count)` positions and the sorted distinct set `{0, count // 2, count - 1}`, plus `{0, 1, 6}` for the full depth-three case. Helper hashes are obtained by calling the maintained `merkleize` on the corresponding subtree. `helperIndices` comes from its `get_helper_indices`; proofs concatenate those hashes in descending order. `emptiedRoot` is obtained by zeroing selected chunks and re-merkleizing.

The maintained root calculators check 270 single paths, 146 multiproofs and 416 replacement roots. The harness separately cross-checks every case with the executable `merkleize_chunks` from consensus-specs v1.5.0 `tests/core/pyspec/eth2spec/utils/merkle_minimal.py` and the positive arithmetic of its `ssz/merkle-proofs.md`. These comparisons found no difference in fixed-depth padding, generalized indices or helper ordering. The maintained fixture is 278705 bytes including whitespace.

**Neither reference is a rejection oracle.** The legacy multiproof verifier can discard conflicting duplicate claims and leave descendants unauthenticated under supplied ancestors; its float `log2` also reports 53 rather than the integer depth 52 for generalized index `2^53 - 1`. No acceptance/rejection verdict is stored in either fixture or used to decide Scalus's negative cases. Those expectations come from the library's strict fixed-depth contract; expected roots also come from independent full rebuilding. The reference's root-claim policy and cache-depth limits are not imported into this API: depth zero and large depths have separate integer/sparse-tree tests.

Tests assert nonzero executed root/proof/update counts for every depth and applicable hash/backend: both hashes on the materialized and streaming builders and independent model; BLAKE2b also as Scala and compiled Plutus V3. Missing groups, removed cases and corrupted expectations must fail. SHA-256 is an off-chain interoperability instance, not an on-chain mode.
