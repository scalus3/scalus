EpochTransition

scalus.cardano.ledger.epoch.internal.EpochTransition
object EpochTransition

The epoch transition: what the ledger does to its state at one epoch boundary, ledger-rules spec section 12.2.

The Emulator runs transition once for each boundary a slot change crosses, in order, spec [EB-1], [EB-1a]: unlike NEWEPOCH (conway Rules/NewEpoch.hs:165), which runs the boundary only when the new epoch follows the last one.

def transition(ledger: State, epoch: EpochBookkeeping, boundary: EpochNo, env: EpochEnv): (State, EpochBookkeeping, ProtocolParams)

The ledger state, the epoch state and the current pparams after the epoch transition into epoch boundary, spec [EB-4], [EB-25], D88. env.params are the current pparams before it.

The ledger state, the epoch state and the current pparams after the epoch transition into epoch boundary, spec [EB-4], [EB-25], D88. env.params are the current pparams before it.

The steps run in the order of the table of spec section 12.2. A step whose phase has not landed is identity, spec [EB-24]. First [EB-5] applies pendingRewards (conway Rules/NewEpoch.hs:172-178), so SNAP sees the paid rewards and the reduced fees. Then, as conway Rules/Epoch.hs:276-378 runs them: SNAP ([EB-6]), POOLREAP ([EB-7] to [EB-9]), the pparams of the enact state ([EB-13]), the enactment of the pending ratify result ([EB-10] to [EB-14]), the voting state ([EB-15], [EB-16]), the treasury ([EB-17]), HARDFORK ([EB-19]) and RATIFY ([EB-20]), then deposited ([EB-18]) on the result: neither HARDFORK nor RATIFY changes a deposit. The blocks made move to the previous epoch and the last epoch becomes boundary, [EB-21] (conway Rules/NewEpoch.hs:182-192). Last, [EB-22] replaces pendingRewards with the reward update of the new epoch, [RW-21], read from the reserves after [EB-5] and from prevParams after [EB-13], [EB-22a].
